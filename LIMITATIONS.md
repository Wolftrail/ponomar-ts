# Limitations

This is a fresh implementation in progress. It currently provides Julian date arithmetic (`JDate`), calendar conversion (`PCalendar`), the Paschalion calculations (Pascha, Pentecost, Lent and Apostles' Fast dates, indiction, solar and lunar cycles), and the `Cmd`/`Value`/`Tone` expression language. Day resolution (`resolveDay`) selects the Triodion, Pentecostarion and Menaion files for a date and returns each commemoration's id and rank, the day rank and the tone; it agrees with the upstream Java engine on 15,342 days across three languages, both lectionary schemes and seven years. Divine Liturgy readings (`getLiturgyReadings`) and Matins readings (`getMatinsReadings`) agree with it on the same days in readings, ranks and origin. Fasting (`getDayFasting`) agrees with it on the same days and, for the localized sentence, on all 128 levels in six languages. `parseBibleReference` is a new implementation of the notation used in the data; it reads every reference in the data except two typos in upstream files (`lives/1777.xml` and `lives/9803.xml`), which it rejects. Commemoration names (`commemorationNames`, `nameForm`), lives (`commemorationLife`) and Liturgy troparia and kontakia (`commemorationHymns`) agree with it on every commemoration of the same days, in three languages. It does not port the original desktop interface. Sunrise and sunset (`getSunriseSunset`, `getSunriseSunsetStrings`) and the Moon's age and phase (`lunarAge`, `lunarPhase`) agree with upstream on about 4,100 sunrise values for eight places (including polar ones) with daylight saving and the twilight altitudes varied, 3,200 localized times in six languages with and without ideographic numerals, and 850 days of the Moon's phase in four languages; real values are compared to within 1e-9 hours or degrees, since the trigonometric functions of Java and V8 can differ in the last bit. The Royal Hours (`composeRoyalHours`) agree with upstream on every day of seven years in four languages, including the propers they take from the Paramony and Good Friday commemorations. The First, Third, Sixth and Ninth Hours (`composeHour`) are composed as a list of typed nodes (titles, prayers with their rubrics, Scripture references, propers from the commemoration data) and agree with upstream on about 5,100 services in English, Church Slavonic (Russian), French and Greek: the type and flags each settles on and the sequence of directives it yields; the prayer, command and title texts agree with upstream's reader in all six languages. Language-pack phrases, repeat counts (`formatTimes`), melody introductions (`podobenIntro`), rank formats (`formatCommemoration`) and the `%getN` reading label (`commemorationLabel`) are available; the label agrees with upstream on every commemoration above, and the numerals (`formatNumber`) on about 5,400 numbers in each of six languages and the root. The vendored XML is converted to typed modules under `src/data/generated/` for the rule files (fasting, service rules, liturgy and scripture-transfer commands), the day files (menaion, triodion, pentecostarion, float), the language packs, the default configuration and the lives (names, biographies, readings, hymns), the last in per-language month chunks plus an id-to-chunk index, the service templates, the per-language prayer and label texts and the Octoechos tables. Day resolution consumes the day files and lives; nothing else uses the converted data yet.

Three upstream data families are deliberately not converted. `Services/Var` holds scratch files that the hour classes write at runtime and read straight back, so the committed copies are a stale snapshot of one run. `Commemorations/` has no reader upstream and its ids appear in no day file. `Services/menaion` holds two Paramony files used only by commented-out code. If a later phase needs them, they can be added to the converter.

One deliberate difference in day resolution: `el/xml/lives/08160600.xml` has a saint's name in a numeric `Type` attribute, which makes upstream throw and abandon that commemoration's remaining files. `commemorationRank` skips such a `SERVICE` and carries on. Whitespace around ids in day files is trimmed, where upstream keeps a stray trailing space in the English `09/01.xml`.

`getLiturgyReadings` returns structured readings (reference, rank, commemoration or weekday), not HTML; placeholders for commemorations without a reading of the requested type are dropped. Upstream throws when a neighbouring day has no Liturgy readings at all while it looks there for transferred readings; this port treats such a day as contributing none. The upstream data in `ScriptureTransfers.xml` is read by no Java code and is not used. Upstream's Matins rules are hard-coded (its `Commands/Matins.xml` does not exist), so `getMatinsReadings` hard-codes them too; it also drops the empty placeholders upstream keeps for commemorations without a Matins reading.

Upstream keeps only the last text chunk of an element, so a life or hymn containing inline `<br/>` or `<p>` (Modern Greek lives) loses everything before the markup; this port returns the whole text, trimmed, with the markup as HTML. Name forms are keyed `nominative`, `genitive`, ... where the data spells the attribute `Genetive`; `nameForm` falls back to the nominative as `getGrammar` does but returns undefined where upstream returns a localized error phrase. Hymns placed directly in a service, outside any section, are reached only through the propers of a service template (`/TROPARION/1`).

`formatNumber` keeps upstream's quirks: a final format with text before its first `#` and none after the last drops the number, a language without number rules gets Chinese numerals up to 4999, and Chinese numerals above 4999 come back as `10000.0`. `formatTimes` trims the text before the number, so Greek gives `ἐκ5`. The `Commemoration2` label supports the first `%getN` call in the phrase only, as upstream. The expression language accepts exponent notation (`1.0E7`) so that upstream's number-to-text substitutions evaluate.

`composeHour` returns nodes, not HTML, and Scripture passages are references (`verses`, or `intro` for an "A reading from..." line) whose text the consumer supplies. Upstream writes the troparion, kontakion and Kathisma choices into scratch files under `Services/Var` and reads them back; the port passes them in memory, so a file left over from an earlier run, which upstream would include, never appears. Upstream always writes the second troparion slot from the first troparion and never the first slot, and the port does the same, so the hour has one troparion. On the days the service rules do not cover (Ascension and the week after Pentecost) upstream fails with a null type, and the port returns an undefined `type` and no nodes. The Kathisma templates spell the heading option `TwoStars` where upstream looks for `2Stars`, so upstream never applies it; the nodes carry `twoStars` for consumers that want it. Upstream cannot write its scratch files for a language with no `Services/Var` directory (Greek) and shows nothing on Lenten days with a Kathisma there, or at the Sixth Hour at all; the port composes them. At the Sixth Hour on Lenten days with a prophecy, the Triodion lives carry none of the hymns the template asks for (`/SEXTE/TROPARION/1` and the prokeimena), so those propers have no text; upstream's null pointer there ends the rest of each included file, and the port keeps all the nodes. Where a proper is found, upstream drops the first character of its raw text; the port trims instead, and the Royal Hours show no difference.

For a fasting level outside the nine named ones, upstream's sentence builder repeats the whole sentence when exactly one food is forbidden (`output += output += ...`); `renderFastingLevel` reproduces that, as it does every other sentence. A day with no applicable fasting rule yields no result, where upstream fell through to an error message.

Bible text is not provided and never will be: supplying a translation is the consumer's responsibility. Only a translation-independent book catalogue (ids, English names, chapter counts) ships, so readings such as `Lk_2:20-21` can be parsed and validated.

The expression language uses standard C-style tokenization and precedence, whereas upstream splits expressions on spaced operators. The two agree on every expression in the vendored data, but unusual unspaced input may behave differently.

Behavior is being added incrementally against the upstream Ponomar Java project. Until a feature is implemented and tested, this package should not be treated as a drop-in replacement for Ponomar.
